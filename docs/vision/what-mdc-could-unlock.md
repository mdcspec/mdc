# What MDC Could Unlock

*The vision anthology: the strongest ideas from five analytical lenses on Markdown Checklists, organized by theme, each with what it unlocks and who cares — ending with the beachhead recommendation.*

This document collects the best of what MDC could become if the format defined in the [format sketch](../spec/mdc-format-sketch.md) succeeds. It is deliberately aspirational; the counterweight lives in [risks, critiques, and open questions](risks-critiques-open-questions.md), and the disciplined subset we will actually build first is in the [MVP definition](../planning/mvp-definition.md). Everything here respects the canonical constraints: strict GFM rendering at L0, one attribute syntax, derived state never stored, and relational features graduating to [.mddb](../spec/mddb-concept-sketch.md) rather than growing the syntax.

## Theme 1: The human–AI shared task substrate

**The file where human and agent meet.** Humans and agents currently share code and chat transcripts but no durable artifact of intention: agent task state is fleeing into JSONL and SQL stores humans won't read — Claude Code's task files, Steve Yegge's [beads](https://github.com/steveyegge/beads) moving to a database after markdown plans became "write-only memory" — while human plans sit in markdown that agents mangle. An MDC file is the natural meeting point: small enough to read in full, structured enough to mutate deterministically, renderable everywhere. *Unlocks:* supervisable autonomy — you audit an agent by reading its checklist and correct it by editing a text file, and the diff shows up in the PR like any other change. *Who cares:* Claude Code, Cursor, and Copilot power users; the [AGENTS.md](https://agents.md) and [MCP](https://modelcontextprotocol.io) ecosystems; engineering leads supervising agent fleets.

**The claim line.** The L2 `claim` primitive is atomic — it fails if an assignee is already set — and because the item line is the merge unit, concurrent claims on different items merge cleanly under plain git. The repo becomes the coordination bus: no server, no queue, and every scheduling decision recoverable from `git log`. *Unlocks:* serverless multi-agent parallelism over a single plan file, with heterogeneous agents from different vendors coordinating through nothing but a repository. *Who cares:* multi-agent framework builders, developers running parallel worktrees, CI vendors wanting agent fan-out without new infrastructure.

**Proof-carrying checkmarks.** The `verify="command"` attribute declares what "done" means in executable terms — the declarative form of [do-nothing scripting](https://blog.danslimmon.com/2019/07/15/do-nothing-scripting-the-key-to-gradual-automation/). Tooling can then distinguish *asserted* from *proven*: a gate can refuse a checkmark whose verify command fails. *Unlocks:* checkbox state that CI, reviewers, and downstream agents can actually trust — the most common agent failure mode (declaring victory on unverified work) becomes a lint error instead of a code-review discovery. *Who cares:* platform/DevEx teams, the checkbox-gating ecosystem that [task-list-completed](https://github.com/marketplace/task-list-completed) already proves demand for, compliance engineering.

**Checklist-as-contract.** The `kind: template` / `kind: run` distinction in frontmatter is formally the schema/instance relationship — the load-bearing abstraction of every serious process product ([Process Street](https://www.process.st), Manifestly) that no plain-text format has ever carried. An agent compiles a spec into a proposed run; a human approves it; execution is bound by the list, and deviation is detectable. *Unlocks:* delegation with checkable acceptance criteria — "review the plan, not the diff" becomes a real workflow. *Who cares:* the spec-driven development community ([spec-kit](https://github.com/github/spec-kit), [Kiro](https://kiro.dev)), engineering managers, and eventually anyone who needs a machine-readable definition of delivered work.

## Theme 2: The tooling universe

**The executable spec as seed crystal.** Following [CommonMark](https://spec.commonmark.org/)'s genome — every rule a testable example, machine-extracted into a conformance corpus — but going one level deeper: MDC's three conformance levels (Render / Parse / Mutate) make it the first markdown spec that constrains *writers*, not just readers. Byte-deterministic mutation is precisely what no incumbent offers and exactly what concurrent human/agent editing requires. *Unlocks:* implementations bootstrappable from the corpus alone; editors, bots, and agents safely co-editing one file. *Who cares:* parser authors across the [remark](https://github.com/remarkjs/remark)/micromark ecosystem (the [MDX](https://mdxjs.com) adoption path), test-infrastructure engineers.

**Exit codes as the workflow API.** The `mdc` CLI treats checklists as programs: `status` for computed rollups, `next --json` for the topologically next actionable item, `check`/`claim` as one-line-diff mutations. Shell scripts and CI compose these the way they compose git. *Unlocks:* checklists as scriptable infrastructure — a release gate is `mdc status` plus an exit code; multi-agent work distribution is `next` plus `claim`. *Who cares:* the todo.txt/Taskwarrior CLI lineage, SREs, release engineers, agent-harness authors.

**Git-native state history.** Because every mutation touches exactly one line, `git blame` reconstructs who checked what, when, in which commit — a compliance-grade audit trail that costs nothing because git already recorded it. Semantic diff/merge drivers are a natural fast-follow. *Unlocks:* concurrent checking without a database — the exact pressure that drove [Taskwarrior to SQLite](https://taskwarrior.org/docs/upgrade-3/) and GitHub to retire tasklist blocks for database-backed [sub-issues](https://github.blog/changelog/2025-01-13-evolving-github-issues-public-preview/), answered with a spec instead of a migration. *Who cares:* git tooling authors, monorepo platform teams, audit-adjacent engineering orgs.

**The .mddb query plane.** When files outgrow the format, the [.mddb concept](../spec/mddb-concept-sketch.md) — an always-rebuildable index in the [Dataview](https://github.com/blacksmithgu/obsidian-dataview)/MarkdownDB lineage, never a source of truth — adds cross-run aggregation: per-item median time-to-check, skip rates, reorder frequency across every run of a template. *Unlocks:* the closed improvement loop Gawande's [test-and-revise discipline](http://atulgawande.com/book/the-checklist-manifesto/) demands but no product delivers — "step 7 is skipped in 40% of runs; delete or automate it," filed as a PR against the template. *Who cares:* [Obsidian Bases](https://help.obsidian.md/bases) and Dataview users, ops teams wanting Process-Street-class analytics without the SaaS, local-first developers.

## Theme 3: Vertical use cases

**Merge-gated OSS release runs.** `RELEASE.mdc.md` in the repo; each release instantiates a run; a CI gate blocks the release workflow until required items are terminal, with `.optional` and cancelled-with-`reason` respected. Every public run file is also viral marketing — watchers see the format in their feeds. *Who cares:* OSS maintainers, release engineers, the supply-chain community ([SLSA](https://slsa.dev)/Sigstore) for whom a sealed run is process provenance beside the SBOM.

**Runbooks-as-code.** Templates with `mode: read-do` or `do-confirm`, pause points, and `verify=` hooks live next to the code they operate; scheduled CI re-runs verifications and files a PR when a runbook decays, so rotten runbooks announce themselves. *Who cares:* SRE and incident response, the [Runme](https://runme.dev)/executable-docs community, self-hosters.

**Compliance-as-code.** Controls as templates, quarterly reviews as runs, N/A-with-reason as first-class honesty, git as tamper-evident timeline. The pitch is portability: your compliance program in plain text, not inside a GRC vendor's moat. *Who cares:* startups facing their first SOC 2, GRC engineers, boutique audit firms.

**Onboarding, labs, and field procedures.** A new hire's 30/60/90 as a run with verification hooks ("repo access works when this command succeeds"); course labs where the test passing checks the box, distributed through GitHub Classroom; versioned SOPs whose change control is literally git. Offboarding runs — access revocation with verification — may be the sharpest single feature. *Who cares:* handbook-first companies, CS educators, quality/safety engineers in the ISO-9001 world.

## Theme 4: Community and ecosystem

**Anchor sequencing.** Court [Obsidian Tasks](https://github.com/obsidian-tasks-group/obsidian-tasks) (~3.7M downloads, an unversioned emoji convention its own users complain about) with a lossless importer and a governance seat; arm agent frameworks with a paste-in skill snippet; earn GitHub last, once in-the-wild usage justifies a Linguist entry. Each anchor conversion yields a converter, a corpus of real files, and users who arrive fluent. *Who cares:* Obsidian plugin developers, agent-framework maintainers, todo.txt refugees.

**Governance with a pre-committed sunset.** Publish the ladder at v0.1: BDFL for velocity, an implementers' council once two independent implementations pass L1, a neutral foundation as the named endgame — designed against the documented deaths of vendor capture and naming wars (see [standards-adoption lessons](../research/standards-adoption-lessons.md)). The [IANA `variant=mdc` registration](https://www.iana.org/assignments/markdown-variants/markdown-variants.xhtml) is a standards foothold no extension-squatter holds. *Who cares:* corporate OSPOs deciding whether to depend on the spec, standards practitioners.

**Importers as the Rosetta stone.** One canonical attribute syntax, with Obsidian emoji, todo.txt, Dataview fields, and VTODO handled as documented importer mappings — converting a decade of incompatible dialects into convertible ones rather than adding a fifth. *Who cares:* migration-tool authors, tool vendors wanting differentiation without forking the format. The naming strategy itself — cede bare `.mdc`, carry identity in-band — is covered in [extension naming conflicts](../research/extension-naming-conflicts.md).

## Theme 5: The deeper why

**Otto's notebook gets an interface.** [Clark and Chalmers](https://consc.net/papers/extended.html) argued that a reliably consulted notebook is literally part of the mind. A checklist file is externalized prospective memory, and the spec's job is keeping the prosthesis trustworthy: deterministic round-trips, no tool silently rewriting what you meant, graceful degradation so the memory outlives its tools. This resolves spec debates on principle — any feature that makes the file less trustworthy as memory violates the format's reason to exist.

**The checkbox as speech act.** An unchecked box is a promise; a checked box is testimony. The format restores the deontology the single bit flattened: who attests, on what evidence, and — via cancellation with `reason=` — the formal right to decline a promise rather than lie about keeping it. The [Haynes](https://www.nejm.org/doi/full/10.1056/NEJMsa0810119)/[Urbach](https://www.nejm.org/doi/full/10.1056/NEJMsa1308261) evidence pair is the design brief: the same checklist saves lives with ceremony and does nothing as a mandate. MDC claims only that it stops *erasing* what makes checklists work — `mode:`, pause points, honest states — never that syntax can compel sincerity.

**Plain text as covenant.** Every rich task system eventually imprisoned intention in a database; plain text is the only medium with a fifty-year unbroken record of readability. The .mdc/.mddb split is the covenant made architecture: the file is canon, the database is commentary — derived, regenerable, never load-bearing. *Who cares:* the file-over-app and local-first movements, archivists, everyone burned by a lossy export ([prior art on markdown databases](../research/prior-art-markdown-databases.md)).

## The beachhead

The recommendation is unambiguous across every lens: **the coding-agent and spec-driven-development community, plus the OSS maintainers they overlap with.** They already write GFM checkbox task files daily; they feel acute pain from fragmented `tasks.md` dialects and write-only agent plans; adoption costs them nothing (files still render on GitHub, per the [landscape map](../research/landscape-map.md), the incumbents are conventions without specs); and distribution is free through skill snippets and MCP servers. The first public proof is the shared human/agent task file — the [MVP](../planning/mvp-definition.md)'s CLI plus teaching snippet, exercised in the [experiment plan](../planning/experiment-plan.md) — where an agent parses, claims, and checks an item and the human reviews a one-line diff. The merge-gated OSS release checklist is the visible second act that carries the format into every repo watcher's feed. Ops, compliance, onboarding, education, and field service are concentric rings, adopted after the developer toolchain exists — because specs follow platforms, and the platform here is the developer toolchain plus the agent harness.
